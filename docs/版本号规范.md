# 版本号规范

> **适用范围**:本仓库所有面向使用者的版本号(git tag / GitHub Release / CHANGELOG)。
> **生效时间**:自 v2.13 起。v2.3~v2.12 为历史编号,**不追溯、不重排**。

## 1. 为什么不照搬 SemVer

[SemVer](https://semver.org/) 的核心变量是 **API 兼容性**,服务于「包管理器判断能否安全升级依赖」。
本项目没有 API、没有下游集成方:使用者是班长 / 辅导员,「升级」= 重新下载一个 HTML 文件。

强行套用只会得到两种尴尬结果:每个版本都填 PATCH(失去区分度),或硬凑一个 MAJOR(其实什么都没破坏)。
因此本项目**借用 SemVer 的位次结构,重新定义每一位的含义**,并换一个机器可判定的发布判据。

SemVer 的第一条铁律仍然遵守:**已发布的版本不可修改**——所以历史编号不重排。

## 2. 发布判据:产物 sha256

> **`python .tools/build.py` 产出的 sha256 变化 → 至少 MINOR;没有变化 → 进「未发布」区,不占版本号。**

这条规则的好处是**机器可判定**,不依赖人自觉。它自动保证「版本号 = 使用者需要重新下载」这一承诺。

## 3. 版本号位次

格式:`vMAJOR.MINOR`(两段式)

| 位 | 含义 | 触发条件 |
|---|---|---|
| MAJOR | 使用者需要重新学,或旧数据 / 旧流程作废 | 交付形态变化(不再单文件)、导出结构变化、五育口径调整、缓存或数据格式不兼容 |
| MINOR | 新增使用者可感知的能力 | 新增功能、界面信息架构调整、性能显著变化、以及「只修错不加功能」的版本 |

**不设 PATCH 位**。原因:本项目每个版本都需要使用者重新下载,MINOR 与 PATCH 对使用者的区别为零,
多一位只会增加噪音。修正类版本仍用 MINOR 编号(如 v2.13),在 CHANGELOG 里如实写清是修正。

## 4. CHANGELOG 结构

- 顶部固定保留 `## 未发布` 区,攒**已提交但产物未变**的改动;
- 已发布版本一条一个标题:`## v2.13 — YYYY-MM-DD`;
- 每条已发布条目必须写 **git tag** 与 **产物 sha256**;
- 分类按需使用 `新增 / 变更 / 修正 / 安全`;
- 最新在上;
- 写「使用者能感知的变化」,不写「重构了哪个模块」——工程细节写进提交信息或 `docs/`。

## 5. 内部版本分层命名

缓存、引擎、数据格式等**内部版本**不得与产品版本同形:

| 用途 | 命名 | 位置 |
|---|---|---|
| 文本缓存格式 | `cache-vN`(如 `cache-v3`) | `TEXT_CACHE_VER` |
| 引擎 / 模型版本 | `engine-ppuN` | 引擎标识 |

历史上 `TEXT_CACHE_VER='v3'` 与产品版本同形,已造成文档里「v3 稳定性加固」这类歧义,后续避免。

## 6. 反例对照

| 反例 | 后果 |
|---|---|
| 一天连发多个版本 | 版本号退化成提交编号,使用者以为经历了多次升级 |
| 发布「产物未变」的版本 | v2.9 曾自述「成品 HTML 未变,本版只修启动器」——版本号失去承诺意义 |
| 版本号与 tag 脱节 | CHANGELOG 有 v2.3~v2.12,远端只有 4 个 tag,追溯时对不上 |
| 重排历史版本号 | 直接违反 SemVer 第一条铁律,并让旧下载链接失效 |
| 内部版本与产品版本同形 | 文档里的「v3」既可能指缓存版本,也可能被误当成产品版本 |

## 7. 一句话总结

**产物变了才发版本;版本号回答「我要不要重新下载」,不回答「改了多少代码」。**
