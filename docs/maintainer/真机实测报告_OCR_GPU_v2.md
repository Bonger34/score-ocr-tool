## 四、【重大发现】整名/模糊检索在 GPU 主路径下 0 命中（原版既有缺陷，v2 沿袭未修复）

### 现象

- 5 个样本 GPU 识别**内容完全正确**（13966 字符真实名单，如 `…2025级电气工程及其自动化2024000001林晓东德育+0.5…`，姓名/学号/分值齐全）。
- 但**整名检索"林晓东"/"陈雨桐"两版均"未找到"**；模糊"学"虽命中 5 个文件，**明细行全部为「无标注 / — / —」（没有解析出任何学号与分值）**。

### 根因链（已逐行定位源码）

1. PPU 引擎输出本身**有分隔**（`ppu_engine_extracted.js` L819：行内 `join(" ")`、行间 `join("\n")`）。
2. **工具层识别入口统一剥离全部空白**：
   - 旧版 L584 `gpuRecognize`：`return t.replace(/\s+/g,'')`
   - v2 L651（单张）/ L690（批）：同样 `replace(/\s+/g,'')`
   - Tesseract 入口 `ocrImageTess`（L520/L551）同样剥空白
   → OCR 文本变成**无分隔紧凑流**（如 `…2024000001林晓东德育+0.5…` 连续拼接）。
3. 解析器 `parseOccurrences`（L423–459+）：`text.split(/[\s|｜]+/)` 分词 → 姓名匹配要求**逐 token 拼接后 `s0===kw`**（L431）。无分隔文本只产生 1 个巨型 token，`s0===kw` **永不成立** → 整名模式返回空 → 0 命中；fuzzy 模式即使子串命中，`parseOccurrences` 同样返回空 → 兜底为 `{score:null,serial:null}` 空记录。

### 影响面

- **GPU/CPU 两条 PPU 路径（即 v2 主引擎路径）**：任何姓名检索 0 命中或空明细——**用户最核心的"查人"功能在当前主路径下不可用**。
- **远程沙盒基准"命中 2 条"成立的机制**：远程无 GPU，两版均走 **Tesseract 回退**；Tesseract 文本含 `|` 与空格（tess_check 缓存样本可见大量 `\|`），`split(/[\s|｜]+/)` 仍可分 token，且远程样本文本质量尚可 → 能命中。**远程基准的命中一致性结论不能代表 GPU 主路径**。
- **本地 Tesseract 已实测异常**（33s/页、输出乱码、大量 `Parameter not found` 警告），回退链在真机不可依赖。

### 修复建议（需用户确认后实施；涉及交付物重建 + 缓存版本变更）

**方案 A（推荐，改动最小且不改解析逻辑）**：识别输出入口的清洗从"剥空白"改为"规范化空白"：
`String(t).replace(/[^\S\r\n]+/g,' ').replace(/[ \t]*\r?\n[ \t]*/g,'\n').replace(/\n{2,}/g,'\n').trim()`
（保留行内空格与行间换行，仅消除多重换行）→ 解析器分词恢复 → 整名/模糊均能解析出学号与分值。涉及 3 处（gpuRecognize / gpuRecognizeBatch / ocrImageTess），缓存版本 v3→**v4**（文本形态变化，旧缓存失效）。
风险：低——分段后解析器见到的是标准分隔文本；`parseOccurrences`、`activityKey`、`dedupe` 逻辑本身零改动。

**方案 B（不动识别输出，在解析前预处理）**：对无分隔文本先做"学号(9位)前/姓名后插空格"规范化再进解析器。改动面更窄但逻辑更 hacky，且仍需缓存 v4。

> 注：`replace(/\s+/g,'')` 自 v1 即存在，**本缺陷非 v2 回归**；但 v2 是当前交付形态，修复应做在 v2 上。

## 七、v2.2 修复（用户真机报障："一开始显示 GPU，跑一会就变成 CPU · 内置 Tesseract（GPU 批识别失败/超时）"）

### 7.1 根因（三条链路叠加）

| # | 机制 | 证据 |
| --- | --- | --- |
| A | **固定 90s 批超时 + 一次失败即永久禁用**：`gpuRecognizeBatch` 用 `withTimeout(..., 90000)` 包 `batchRecognize`，catch 里直接 `gpuDisable('GPU 批识别失败/超时')`。密集表格/扫描页单页可达 15~20s，6 页一批（OCR_CHUNK=6）就会顶到 90s | 交付物原文即此文案，与用户截图逐字一致 |
| B | **超时后底层 run 仍占用会话**：`withTimeout` 只是 race，不取消 ORT 的 run；下一批进链后撞 `Session already started` → 被 10-B 判为"引擎损坏" → 又一次 `gpuDisable` | 互斥链 `gpuEnqueue` 只等 race 结果，不等底层 promise |
| C | **实际跑在核显上**：浏览器 GPU 进程默认绑定 Intel Iris Xe，WebGPU 随之用核显；核显驱动在长跑高负载下更易 TDR/device lost，触发 A/B | 状态栏 `GPU · Intel Iris Xe`；加 `--force_high_performance_gpu` 后变 `NVIDIA GeForce RTX 2050` |

### 7.2 修复内容（v2.2，交付物已更新）

1. **超时按页数自适应**：`60000 + 页数×60000` ms（6 页 420s / 3 页 240s / 1 页 120s），不再用固定 90s 误杀正常慢批
2. **失败降批重试而非永久禁用**：失败 → 批上限减半（6→3→1）+ 本批回退内置 → 后续批继续用 GPU；**连续 6 批**（含重建会话后重试）都失败才彻底回退
3. **会话污染重建**：失败后置 `gpuStale`，下次 `gpuInit` 先等旧 run 收尾（最多 ~15s）再丢弃重建，避免新旧会话同时占显存而初始化 OOM
4. **互斥链等待底层 run 真正 settle**：`gpuChain` 挂 `raw.then(...)`（带 15s 宽限），杜绝"超时后并发 run"引发的连锁 `Session already started`
5. **批内部分失败不再拖垮全局**：`bad < res.length` 时保留成功项（失败项逐页回退内置），只降批
6. **块大小随批上限动态收缩**：`chunkN = min(OCR_CHUNK, gpuBatchLimit)`
7. **初始化失败允许重试一次**（连续 2 次才永久禁用），避免重建时显存瞬时不足直接判死
8. **核显显式标注 + 切独显提示**：状态栏显示"（核显）"，悬停给出 `启动工具.cmd` / Windows 图形设置指引
9. **启动器强制高性能 GPU**：`启动工具.cmd`、`serve_ocr.ps1` 改为用 Chrome/Edge + `--force_high_performance_gpu` 打开
10. 顺带修 GPU 名重复（`Intel Intel …` → `Intel …`）

### 7.8 v2.3 修复：串行队列回归（用户实测"第一批就卡死、秒数也不增加"）

**现象**：用户用真实全量包（285MB / 497 个 PDF / 2077 页）实测，点"开始解析"后**第一批即卡死**，状态栏"已用"秒数不再增加。

**复现与取证**（Playwright + 同一压缩包）：

| 手段 | 结果 |
| --- | --- |
| CDP `Runtime.evaluate` 主动查询 | 完全无响应（主线程被占死） |
| 进程 CPU 采样 | 15s 内涨 16s（单核满载），非阻塞等待 |
| `Debugger.pause` 抓栈 | 全部为 wasm 帧 + emscripten 胶水（`$func*` / `$Fc` / `$Tb`） |
| `sendBeacon` 打点（页面卡死也不丢） | **定位到根因**，见下 |
| 对照组 | 不勾 OCR 同一包 190s 正常跑完 511 文件；单文件勾 OCR 正常 |

**sendBeacon 时间线（点击"开始解析"后）**：

```
14.3s handleRun ENTER
14.8s file.arrayBuffer OK          ← 读 285MB 正常（0.5s）
15.2s JSZip.loadAsync OK files=762 ← 正常
15.5s unzip OK ×6                  ← 6 个文件并发解压正常
16.3s batchRecognize ENTER n=1     ← 第 1 批
20.2s batchRecognize OK            ← 成功
20.2s batchRecognize ENTER ×5      ← ★ 5 个批同时涌入同一 ORT 会话
（此后主线程冻结）
```

**根因**：v2.2 把 `gpuChain` 的更新写进了 `then` 回调内部。同一批微任务里先后进入的多个批**都读到同一个旧链头**，互斥链失效 → 6 个文件的批识别同时冲进同一个 ORT 会话 → 会话错乱 + 主线程被 wasm 占满 → 页面假死。**这是 v2.2 引入的回归**（v2.1 的 `gpuEnqueue` 在调用时同步推进链头，行为是正确的）。

**修复（v2.3）**：新增 `gpuQueue(makeRaw)` —— **调用即同步占位**，链上等待底层 `run()` 真正 settle；`withTimeout` 只影响调用方（超时后本批回退内置），不会让下一批提前进入会话。

**验证（同一 285MB 全量包，独显）**：修复后状态栏持续推进（10s→93 个文件 / 286s），识别心跳正常跳动，`gpuFails=0`、`tessFallbacks=0`，CDP 全程可响应，无卡死。

> 影响面：凡 zip/多文件中存在多页并发 OCR 的场景都会触发（与文件大小无关，46MB 包同样复现）。

### 7.9 v2.4 提速（用户问"能不能再加快速度"，以 `target/` 真实语料为准）

**先量分母再动手**：用 pdf.js 逐页复刻工具判定（`getTextContent()` trim 后为空才 OCR），统计 `target/` 全部 9 个文件：

| 指标 | 值 |
| --- | --- |
| 文件数 / 总页数 | 513 个 / 2202 页 |
| **需要 OCR 的页数** | **188 页（8.5%）**，集中在 81 个文件 |
| 有文本层的页数 | 2014 页（91.5%，其中 107 页 / 104 页等大文件全是文本层） |

即：**OCR 不是全部工作量，解析侧（pdf.js 文本层提取）同样是硬成本**，优化必须两边一起看。

**分项计时（探针 `perf_matrix.py`，同一 24 页密集样本 008__，独显，冷缓存）**：

| 项 | 基线 v2.3 | 说明 |
| --- | --- | --- |
| 单页总耗时 | 2.11s | 24 页 50.7s |
| det（含 CPU 预处理+后处理） | 0.22s/页 | detRun 0.15s |
| **rec 合计** | **1.89s/页** | recRun 1.35s + CPU 1.89-1.35=0.54s |
| rec 回读量 | **11.1 GB / 24 页**（≈462MB/页） | 输出张量 `[B,T,18385]` fp32，18385 类 × 4B = 73.5KB/时间步 |
| 单次 rec run | 125ms | 动态批 4；实测回读带宽仅 ~0.35GB/s |

**根因**：rec 模型末端是 `Softmax → [B,T,18385]`，每个字符约 6 个时间步 → **每字符 159KB 回读**。GPU→CPU 回读 + 主线程逐类扫描求 argmax（每批 1070 万次读取）吃掉了 rec 路径的绝大部分时间，且在多文件并发时把主线程占满（OCR 与解析互相拖累）。

**修复（三处，全部实测验证）**：

1. **模型侧：把 argmax 搬进 ONNX 图**。用自写的极简 protobuf 编辑器（`.tools/onnx_tool.py`，无需安装 onnx 包）在 rec 模型末尾追加
   `ArgMax(axis=2) → Cast(f32) → ReduceMax(axes=[2]) → Concat(axis=2)`，图输出由 `[B,T,18385]` 变为 **`[B,T,2]`（索引 + 该位置最大概率）**。
   - 数值一致性：与原模型在同一输入上逐元素比对 `badIdx=0 / badMax=0 / maxDiff=0`（索引与概率完全一致）。
   - 回读量：40.68MB/批 → **0MB（1.2MB / 24 页）**，降 4 个数量级。
   - 单次 run：193ms → 94ms（B=4,W=1160）；W=3232 时 426ms → 244ms。
2. **引擎侧：注入"索引解码"分支**。构建脚本在 PPU 引擎源码里加 `decodeIdxRow()`，`output.dims` 为 `[B,T,2]` 时走新路、否则退回原概率解码——**补丁对旧模型同样安全**。
3. **参数侧**（三项，均有实测支撑）：
   - 解析并发 `CONC 6 → 14`。实测 pdf.js 文本提取的并行效率只有 ~4×（worker 大量时间在等主线程/IO），因此提高并发是净收益：**解析侧全量（不勾 OCR）200s → 171s → 161s（CONC 6 / 10 / 14）**。
   - zip 条目解压改用浏览器原生 `DecompressionStream`：60 个条目 / 152MB 实测 6012ms → 2652ms（**2.3×**），且解压由浏览器原生线程完成、不再长时间占用主线程；非 deflate / 长度不符 / 无该 API 时自动退回 JSZip 原路径。
   - `recBatchSize 4 → 8`（回读不再是瓶颈后，批大小只影响固定开销摊薄；实测 8 比 4 快 3%，16/32 反而更慢）。同时 `gpuBatchFail` 新增"失败时同步把 rec 批大小减半（8→4→2→1）"——原来只降每批页数，而显存大头其实是单次 rec run 的中间张量 `[B,T,18385]`；会话重建后恢复默认。
   - pdf.js 取词加 `disableFontFace:true, useSystemFonts:false`：文本密集 PDF 实测提取提速约 12%、**提取字符数完全一致**（只取字符、不装配字体）。

**实测（008__，24 页密集样本，独显，冷缓存）**：

| 配置 | 单页耗时 | rec GPU | 备注 |
| --- | --- | --- | --- |
| v2.3 基线（旧模型，批 4） | 2.11s | 32.4s | 回读 11.1GB |
| v2.4（新模型，批 4） | 1.71s | 25.4s | |
| **v2.4（新模型，批 8）** | **1.66s** | **24.1s** | 采用（显存吃紧时自动降到 4/2/1） |
| v2.4（新模型，批 16 / 32） | 1.82s / 1.91s | 26.9s / 28.9s | 批过大反而慢 |

**全量实测（`target/` 全部 9 个文件，冷缓存，`corpus_phase.py`）**：

| 版本 | 总耗时 | 命中文件 | gpuFails | tessFallbacks | 渲染累计 |
| --- | --- | --- | --- | --- | --- |
| v2.3 | **743s（12:23）** | 525 | 0 | 3 | 196s |

| **v2.4 最终（CONC=14 + 取词选项）** | **292s（4:52）** | **525（一致）** | 0 | 3 | 84s |

→ **2.55× 提速**，命中文件数完全一致。密集单页样本只快 1.2×，全量快 2.55×：真实语料里 OCR 页多为 1–3 页的小文件（固定开销占比高），且 v2.3 的主线程被 argmax 解码占满时解析侧也被拖慢——去掉解码后解析侧同时受益。

> 解析侧地板：同一语料**不勾 OCR** 为 **161s**（pdf.js 文本层提取 2014 页 + 解压）。即 v2.4 的 292s ≈ 161s 解析 + 131s OCR，两侧已大致相当；后续再提速要动解析侧（pdf.js 内部）或换更小的 rec 模型。

#### 7.9.1 环境敏感性（重要，影响复测口径）

本机 GPU 是 **RTX 2050 4GB**，实测空闲时也常被桌面程序占用：`nvidia-smi` 显示 **2611/4096 MiB 已用、利用率 55–100%**（占用方为 Edge/EdgeWebView2、微信、QQ、WorkBuddy 等）。

后果：在 GPU 被占满的时间窗内，**两版都会出现批识别失败 → 连续 6 次后回退内置 Tesseract**，整场耗时从 5 分钟量级退化到 12–30 分钟（同一版本实测 292s / 364s / 469s / 771s / 1664s 都有，其中 1664s 那次 139 页走了 Tesseract、命中文件数从 525 变成 524——即回退路径的识别质量与主路径不同）。这是 v2.2 之前就存在的环境问题，不是 v2.4 引入的；v2.4 已把"失败时降 rec 批大小"也纳入降级链，进一步降低显存峰值。

**建议**：跑全量前关掉不用的 Edge 标签页/微信视频等占 GPU 的程序；状态栏若出现"GPU 批识别失败…"即为该场景。若需要长期在 GPU 紧张时也能跑，可把 `recognition.recBatchSize` 直接设为 2。

**准确率验证（拒绝以精度换速度）**：

| 候选改动 | 提速 | 逐页 OCR 文本比对 | 结论 |
| --- | --- | --- | --- |

## 7.11 v2.6 进度条与倒计时准确性 + 隐私自检（用户要求"提升进度条与倒计时的准确性；HTML 里不要出现任何个人隐私，特别是真实姓名"）

### 7.11.1 旧引擎为什么不准（先定位，再改）

旧实现把工作切成"单元"（一页 PDF 算 1 个单元、一个 zip 内部文件算 1 个单元），
进度 = 已完成单元 / 总单元，剩余时间 = 剩余单元 × 每单元平均耗时。三个结构性缺陷：

| 缺陷 | 实测后果 |
| --- | --- |
| 一页 OCR 与一张 xlsx 都算 1 个单元，耗时差上千倍 | 进度条按"页数"走而非"工作量"走，扫描件占多时严重失真 |
| 只在单元完成时刷新（OCR 一批 6 页，一批要 19s 才刷一次） | "已用 / 预计剩余"整段冻住——真机采样到 **107.1s** 不刷新 |
| 分母只含"已打开的文件"，尚未打开的文件完全不计 | 最后一个文件刚开头进度条就冲到 98% 不动，倒计时假性归零（实测 80% 处显示 0:02，实际还剩 24s） |

### 7.11.2 新引擎（v2.6，`makeProgress()`）

把每一步折算成**预计工作量（毫秒）**，进度 = 已完成工作量 / 总工作量：

| 机制 | 作用 |
| --- | --- |
| 按类型计权：OCR 页 1600ms（CPU 回退 8000ms）、文本页 25ms、文件 150ms、检索按文本量 | 进度条按真实工作量走，扫描件不再拖住整条 |
| 分母 = 已登记工作量 + **未打开文件按体积外推的墙钟时间**（×1.6 保守系数） | 最后几个文件也有预留份额，进度条不会提前冲到 98% |
| 实测速度：从"第一个单元完成"起算的全程平均（70%）+ 1 秒窗口 EMA（30%） | 首个页面含模型预热/着色器编译，算进去会严重低估速度；全程平均压掉"一批 6 页"的脉冲 |
| 在途外推（creep）：`(距上次完成的时间) × 速度`，上限取"剩余工作量的 98%"与"一批（6 页）"的较小者 | 一批 6 页要 19s，中间进度条也会匀速前进；同时防住"一页卡很久"时冲顶 |
| 250ms 定时重绘 + 百分比单调不回退 + 进度条与数字同源 | "已用/预计剩余"连续跳动；zip 展开导致分母变大时只停不退 |
| 解析 0–98%、检索 98–100%；`finish()` 兜底 + `finally` 停表 | 检索只在内存扫字符串（通常 <1s），不再空占 15% 进度条；异常也不会留下定时器 |

## 7.13 v2.8 导出材料包（用户问"能否直接导出为格式化的文件夹压缩包"）

**能。** 结果区新增「导出材料包」按钮：按 `学号姓名/五育测评/分值 + 原文件名` 打包**命中的名单原件**
（文件名保持原样，只在最前面加分值），包内附 `说明.txt`（口径与上限提醒）与 `清单.csv`（学号/姓名/五育/加分值/事由/材料文件名/来源名单文件）。

### 7.13.1 为什么装的是"名单原件"

工具只读用户放进去的名单文件（zip / PDF / xlsx），从不接触学生上传的证明材料，
所以能放进去的就是命中的名单原件——它正是"谁在哪个名单里、加了什么分"的凭证。
需要"班级"这一层目录时，自行在外层再套一层即可（工具不知道班级信息）。

### 7.13.2 三个实现要点

| 要点 | 做法 | 为什么 |
| --- | --- | --- |
| 保留来源 | 解析时给每条结果挂 `{file, zip内路径}` 与体积 | **只记引用、不复制字节**。若直接持有 JSZip 的 ZipObject，其压缩数据是原包视图，285MB 的包会被整场驻留 |
| 取字节 | 导出时按来源文件逐个取，同一份 zip 只解一次，导出结束即清缓存 | 峰值内存只与"当前这一个来源文件"有关 |
| 体积守卫 | 预估 > 300 MB 直接拒绝，并提示先精确检索 | 模糊检索会命中 458 份名单，逐项复制约 28 GB |
| 命名 | **原文件名保持不变，只在最前面加分值**（`+2 晚归打卡公示汇总.pdf`）；非法字符 `\ / : * ? " < > |` 换 `_`、去结尾点与空格、重名加 `(2)`、截断只截名字不截扩展名 | 用户要求"原文件名不变"；Windows 与常见解压软件另有字符限制 |
